# 为什么纯视觉不够

> 讲一个反直觉的结论：**截图 + 视觉大模型**这个看起来最"通用"的方案，
> 在真实桌面自动化里是**最慢、最贵、最不可靠**的那条路。

---

## 先看一个数字

"找到那个确定按钮"，三种方法：

| 方法 | 耗时 | 成本 | 准确度 |
|---|---|---|---|
| **UIA 语义查找** | ~2ms | 0 | 精确到像素 |
| **CDP 读 DOM** | ~20ms | 0 | 精确到像素 |
| **截图 + 视觉大模型** | ~3000ms | ~1400 token | **模型可能编造坐标** |

**差三个数量级。**

如果你的 Agent 每个动作都要走视觉，那么：

- 一个 20 步的任务要 **60 秒**（全是等待）
- 烧掉 **28000 token**
- 而每一步都有 **5~10% 的概率**拿到一个错坐标

---

## 纯视觉的三个硬伤

### 1. 慢

一张 1280x720 的图，光上传就要几百毫秒。
加上视觉推理，单次 2~5 秒是常态。

**这在"循环操作界面"的场景里是致命的** ——
Agent 做一次动作要等 3 秒，那它和人手操作比毫无优势。

### 2. 贵

按 `w*h/750` 估算，1280x720 约 **1229 图像 token**。
加上 prompt 和输出，一次请求轻松 1500+。

**一个 20 步的任务 = 30000 token。** 按 GPT-4o 的价，约 $0.15。

单次不贵，但 Agent 是**跑循环**的。一天跑 100 次任务就是 $15。

### 3. ⚠ 最要命的：**模型会编造坐标**

这不是"偶尔出错"，是**结构性的**：

- 它被训练成"给出答案"，而不是"承认不知道"
- 它看到的是**压缩后的图**，坐标天然有偏差
- 它对"像素"没有真实概念 —— 只是在生成看起来合理的数字

这个失败模式是**设计时就必须假定的**：给一张全空白的截图问
"确定按钮在哪"，模型很可能返回一个坐标 + `confidence: 0.7` ——
它被训练成"给出答案"，而不是"承认不知道"。

**而那个坐标会被拿去点击。** 点错地方比"停下来"危险得多。

（`validator` 的第三道闸门就是为这个准备的：不跟模型辩论，
直接量那块区域的像素方差。**用真实像素否证模型的说法**，
与它说什么无关。）

---

## 那正确的做法是什么

**分级降级**。按**成本**排序，不是按准确率：

```
UIA  →  CDP  →  OCR  →  模板匹配  →  视觉大模型
~2ms   ~20ms   ~300ms   ~500ms       ~3s
```

### 为什么是这个顺序

**贵的层先跑等于每次查找都付最贵的代价。**

代价是后面几层很少有机会跑到 —— **那正是目的**。

设计时的**预期**分布（操作普通 Windows 应用）：

| 层 | 预期命中率 |
|---|---|
| UIA | ~70% |
| CDP | ~15%（网页场景更高） |
| OCR | ~8% |
| 模板匹配 | ~5% |
| 视觉大模型 | **~2%** |

> ⚠ **这是设计意图，不是 benchmark 结果。** 本项目没有跨大量真实
> 应用的命中率统计 —— 那需要一套标注数据集，目前没有。
>
> 表里的比例想说明的只有一件事：**降级链的形状** ——
> 绝大多数查找应该在前几层解决，最贵那层只兜底。
> 具体数字别当真，形状是真的。

### 每一层补上一层的盲区

| 层 | 能看见什么 | **看不见什么** |
|---|---|---|
| UIA | 暴露了无障碍信息的控件 | 自绘界面、canvas、游戏 |
| CDP | 网页 DOM（最准最快） | 非浏览器 / 没开调试端口 |
| OCR | 屏幕上的**文字** | 图标、图形、纯色按钮 |
| 模板匹配 | 长得像模板图的区域 | 界面改版后失效 |
| 视觉大模型 | 什么都能认 | 慢、贵、会编造 |

**没有一层能覆盖所有情况** —— 所以答案是"全都用，按成本排"。

## 如果非要用视觉，怎么用才安全

**四道闸门**（本项目在 `avatar/vision/validator.py` 里实现了）：

```
模型返回 (x, y, confidence)
        │
        ▼
① 范围校验    0 ≤ x < 宽 且 0 ≤ y < 高
        │
        ▼
② 坐标换算    图像 → 原图 → 屏幕（漏了会整体偏移 2.3 倍）
        │
        ▼
③ 像素校验    周围 50x50 区域必须有颜色变化
        │
        ▼
④ 置信度阈值  confidence ≥ 0.5
```

### ③ 是最有价值的一道

**它用真实像素否证模型的说法。** 前面两道是算术，只有这道是"看图说话"。

判据是 **50x50 区域的灰度方差**：

- 纯色背景 → 方差 ≈ 0 → 拒绝（模型在空白处报了个坐标）
- 有文字/边框/渐变 → 方差 > 8 → 通过

**为什么用方差而不是"有没有非背景色"**：因为**不知道背景色是什么**。
深色主题的按钮可能是浅灰，浅色主题的可能是深灰 ——
按颜色判断两头不讨好。方差只问"这块有没有变化"，**与主题无关**。

### 失败要返回"不知道"，不是"猜一个"

校验失败意味着"我们**不知道**目标在哪"。这时候：

- **不能**用原始坐标凑合（那是盲点）
- **不能**返回"最接近的"候选（那是猜）
- **不能**抛异常（调用方还要继续沿降级链走）

**返回 `None` + 详细原因。**

## 一个反例：为什么"全视觉 Agent"在 demo 里好看、在真实环境里碎

demo 里通常是：

1. 干净的系统主题（浅色）
2. 固定的分辨率（1920x1080，100% 缩放）
3. 稳定的应用版本
4. 没有其他窗口干扰

真实环境里：

1. 深色主题 / 高对比度主题 / 自定义主题
2. 2K / 4K / 多显示器 / 125%~200% 缩放
3. 应用刚更新，按钮挪了位置
4. 有通知弹窗、有其他窗口遮挡

**纯视觉方案在这四种变化下全都会退化。**
而 UIA 方案对 1、2、4 是**免疫**的（它读的是控件树，不是像素）。

## 小结

| 结论 | 理由 |
|---|---|
| **能用协议就别用鼠标** | CDP 比模拟点击快 40 倍 |
| **能用语义就别用视觉** | UIA 比视觉大模型快 1500 倍 |
| **视觉是最后手段** | 它慢、贵、且会编造 |
| **非要用就必须校验** | 四道闸门，一道不能少 |

**"通用"不等于"好用"。** 一个什么都能做但每次要 3 秒的方案，
在真实工作流里打不过一个只能做 70% 但每次 2ms 的方案 ——
因为剩下的 30% 可以再降级。
