# "除了必要全是自动"的产品哲学

> 讲一个产品决策：**什么时候该让 Agent 停下来。**

---

## 一句话

**除了必要全是自动。**

这里的"必要"指的是：**机器做不可靠、且做错代价高的事。**

---

## 一个失败的产品长什么样

### 反面一：什么都自动

> "我们的 Agent 全自动！从登录到下单，全程无人干预！"

**问题**：撞上验证码怎么办？

- 想办法绕过 → **违反服务条款**，而且用户账号有风险
- 硬着头皮点 → **点错地方**，可能下错单
- 卡住 → 用户不知道发生了什么，**任务静默死掉**

**三种都很糟。**

### 反面二：什么都问

> "每一步都让用户确认"

**问题**：那不叫自动化，叫"带提示的手动操作"。

用户要的是"我说一句话，它做完"，不是"我说一句话，
然后点 20 次确认"。

---

## 正确的分界线在哪

**判据有两条，同时满足才该自动**：

1. **机器做得可靠** —— 有确定的方法，不是猜
2. **做错代价可接受** —— 错了能重试，不会造成不可逆损失

### 该自动的（绝大多数）

| 场景 | 为什么可靠 | 错了会怎样 |
|---|---|---|
| 打开程序 | UIA 能精确找到 | 重开一次 |
| 输入文字 | SendInput 是确定行为 | 删掉重输 |
| 点击按钮 | UIA/坐标定位 | 重试 |
| 网页操作 | CDP 直连 DOM | 重试 |
| 读数据 | 协议读取 | 重读 |
| 保存文件 | 快捷键 | 重存 |

**这些占真实工作流的 95%+。**

### 该停下来的（少数，但关键）

| 场景 | 为什么不可靠 | 错了会怎样 |
|---|---|---|
| **验证码 / 滑块** | 机器解题不可靠 | 账号被风控 |
| **点选文字验证** | 同上 | 同上 |
| **需要业务判断** | 模型不懂你的业务 | 决策错误 |
| **不可逆操作** | 删库、转账 | **灾难** |
| **登录密码输入** | 涉及凭据 | 泄露风险 |

**这些不到 5%，但一旦出错就是大问题。**

## 具体怎么实现"该停就停"

### 检测层：三层判定

```python
from avatar.risk_detector import detect

st = detect(hwnd)
if should_intervene(st)[0]:
    guard(st, hwnd=hwnd)      # 停下，叫人
```

三层检测（DOM → 窗口 → 像素）—— 一层看不到就看下一层。

### ⚠ 判据是 `is_clean`，不是 `detected`

这是本项目一个**刻意的设计**：

```python
# ❌ 直觉写法
if st.detected:
    stop()

# ✅ 本项目的写法
if not st.is_clean:
    stop()
```

**区别在哪**：`detected` 是"**确认**有验证题"，
`is_clean` 是"**确认**没有"。

中间那个状态 —— **"不确定"** —— 两者都不算。

**"不确定"必须停下来。** 因为：

- 如果其实有验证题而你继续 → 撞上去
- 如果其实没有而你停下 → 用户按一下 F9 就好

**代价不对称，所以保守。**

### 熔断层：怎么叫人

```python
guard(st, hwnd=hwnd)
```

它做四件事：

1. **响铃** —— 三声提示音（`winsound.Beep`）
2. **桌面通知** —— 一个置顶的小窗口，说明情况
3. **等 F9** —— 人处理完了按 F9 继续
4. **超时降级** —— 等太久就记下现场截图，然后按配置决定

**关键是第 3 步**：它真的**阻塞**在那里，不是"标记一下继续跑"。

## 为什么不做"打码平台默认开启"

打码平台能解决验证码问题，但本项目**默认关闭**。

**理由**：

1. **要花钱** —— 每次几分钱，但 Agent 是跑循环的
2. **隐私外发** —— 要把截图发给第三方
3. **它在"绕过风控"** —— 这本身是个立场问题

**默认关闭，但要能用**：

```bash
set AVATAR_SOLVER_ENABLED=1
set AVATAR_SOLVER_API_KEY=...
```

**显式打开 = 用户明确知道自己在做什么。**

---

## 一个容易被忽略的点：**停下之后要能继续**

"停下来"不是终点。真正的工作量在**恢复**：

```python
# 熔断时的现场
{
    "step": "s3",
    "reason": "检出 slider",
    "screenshot": "/path/to/xxx.bmp",
    "waited": 0.0,
}
```

**恢复后要能回答**：

- 停在哪一步？
- 已经做完了哪些？
- 重来会不会重复做？

所以本项目有**断点恢复**：

```bash
python -m avatar tasks --resume <task_id>
```

**已成功的步骤不重跑**，失败/卡住的重新进入调度。
自愈计数**跨恢复累加**（不会因为重启就重置重试上限）。

## 三层"停"的粒度

| 粒度 | 什么时候 | 机制 |
|---|---|---|
| **单步暂停** | 这一步需要人看一眼 | `pause_for_human` |
| **任务熔断** | 检出风险 | `guard()` → 整个任务暂停 |
| **全局停止** | 人主动叫停 | Ctrl+C / 外壳菜单 |

**为什么要分三层**：

- 单步暂停是"继续跑，但先确认这一步"
- 任务熔断是"整个会话有风险，全停"
- 全局停止是"我不想跑了"

**混在一起会导致**：一个小小的确认也要重启整个任务。

---

## 这个哲学的另一面：**默认值要保守**

"除了必要全是自动"的推论是：

**所有危险的能力，默认关闭。**

| 能力 | 默认 | 理由 |
|---|---|---|
| 打码平台 | **关** | 花钱 + 隐私外发 |
| 视觉大模型 | **关** | 花钱 + 隐私外发 |
| LLM 规划 | **关** | 花钱 + 隐私外发 |
| 点击穿透 | 开 | 不挡用户 |
| 真人化输入 | **开** | 安全优先 |
| 风控闸 | **开** | 硬约束 #9 |

**判据**：这个能力的**失败模式**是"多花钱"还是"出事"？

- "多花钱" → 可以默认开
- "出事" → 默认关，让用户显式打开

---

## 小结

| 问题 | 答案 |
|---|---|
| 什么时候自动 | 机器可靠 **且** 错了可恢复 |
| 什么时候停 | 机器不可靠 **或** 错了不可逆 |
| 不确定时 | **停下来**（代价不对称） |
| 危险能力 | 默认关，显式打开 |
| 停下之后 | 要能恢复，且不重复做 |

**"全自动"不是目标，"该自动的自动、该停的停"才是。**

一个 95% 自动 + 5% 精确打断的 Agent，
比一个 100% 自动但会在关键时刻点错的 Agent，
**可靠得多，也可用得多。**
