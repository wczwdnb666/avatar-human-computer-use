## 0. 这份文档要解决的问题

风险检测器的核心矛盾只有一句话：

> **判早了，正常流程被无谓打断；判晚了，验证题把任务撞死。**

本项目的产品哲学是「**除了必要全是自动**」。这句话听起来是
"尽量别打断"，但它真正的含义更难做到：

- **必要**不是"这个看起来像验证题"，
  而是"**人类介入真的有意义**"。
- 一个 100% 确定是滑块验证题的页面，如果人是唯一能过的，
  它就是**必要**的。
- 一个只有 30% 像验证题的页面，如果人来了也只能干瞪眼，
  它就**不必要**。

所以整套模型有两个正交的轴，**不要把它们混在一起**：

| 轴 | 回答的问题 | 取值 |
|---|---|---|
| `type` | 这是什么 | captcha / slider / otp / rate_limit … |
| `severity` | 该不该打断 | info / bypassable / interrupt / block |

同一个 type 在不同场景下 severity 不同。Cloudflare 的
`challenge_page` 在无感盾下是 `bypassable`（等一下自己就过），
在"检查您的浏览器"卡死时是 `interrupt`（人点一下就过）。
**这就是为什么 severity 是逐条指纹配的，不是按 vendor 配的。**

## 1. 最强的一条设计原则：反证按「在正常页面的普遍程度」排权重

### 1.1 结论（先看这个）

弱词（"验证""登录""确定""隐私政策"这类高频词）**不参与加分，
只参与扣分**。扣分力度按下面这一条原则排列：

> ## 一个词越常出现在正常页面上，它作为风险证据的反证力度就越强，扣分就越狠。

具体分档：

| 档 | 惩罚 | 判据 | 词例 |
|---|---|---|---|
| `footer` | **-0.30** | 几乎只在正常页面出现：页脚法律条款、导航栏登录按钮 | 服务条款、隐私政策、登录、注册、cookie、版权、关于我们 |
| `ambiguous` | -0.15 | 高频但**有歧义**：既可能是正常文案，也可能是验证题文案的一部分 | 验证、确认、确定、人机、检测、提交 |
| `ocr_noise` | -0.05 | 几乎无信息量：OCR 会把任何页面都读出这些 | 正在、加载中、请稍候、loading、请等待 |

### 1.2 为什么是"反证按普遍程度"，不是"按词的误导性"

这是本项目里**唯一一条被我推翻过的设计方向**，值得完整记下来。

**最初的方案**（兄弟提的）是：

> 高频弱词 → -0.10，中频弱词 → -0.20

也就是按「**这个词有多像风险信号**」排：因为"验证"这个词长得
就像验证题，所以把它扣得狠一点，压住它的误导性。

**方向错了。** 理由有三层，一层比一层硬：

**第一层：惩罚是扣分，扣得越多越倾向判"干净"。**
所以"扣得狠"= "更相信这是正常页面"。
按原方案，`登录/隐私/条款` 扣 0.10，`验证` 扣 0.20 ——
等于说"我拿'登录'当干净页面的证据，比拿'验证'更弱"。
但事实上：

- 页脚出现"隐私政策/服务条款/cookie"，**100% 的正常站点都有**，
  而验证题页面几乎不会有完整页脚。
- 页面出现"验证"两个字，**验证题和正常站点都可能有**
  （"验证邮箱"按钮到处都是）。

**越普遍 = 越能反证"这是验证题"。所以页脚档必须扣得最狠。**

**第二层：实测数据是最强反证。**
本机拿一段真实的电商站页脚文本跑：

```
"欢迎来到本站 登录 注册 隐私政策 服务条款 关于我们 联系我们 版权 cookie 版权所有"
→ score = -2.70，weak_penalty = -2.70，tiers = {footer: 9}
→ detected = False（正确地判为干净）
```

同一段文本，**把页脚档惩罚清零**（`penalty_scale={footer: 0.0}`）：

```
→ score = 0.00，detected = False
```

也就是说：这段文本里没有任何正向证据，**全部的反证力度都来自
页脚档**。如果按原方案把它压到 0.10，page 上只要再叠一两个
`ambiguous` 档的"验证/确认"，总分就会被推过阈值 → 误报。

**第三层：5G 的误报率测试就是要压这个。**
分档不只是分类，它是**可消融的开关**：

```python
text_hit_score(text, penalty_scale={WEAK_TIER_FOOTER: 0.0})
```

这一行就是"把页脚反证关掉"，用来量化这一档到底贡献了多少
误报率下降。没有分档就没法做这个消融实验，
"页脚是最强反证"就只能是一句无法验证的断言。

### 1.3 量级的选择

保留兄弟给的 **0.10 / 0.20 的量级**，等比放大到
**0.05 / 0.15 / 0.30** —— 三档的**相对关系**比绝对值重要，
而且 0.30 这个量级刚好让"只有页脚、没有正证据"的长文本
落到明确的负分区间（见上面的 -2.70）。

### 1.4 这条原则的推广（写给以后）

"按在正常语境的普遍程度排权重"不止适用于中文弱词。
任何人加新指纹时都应该问一遍：

> 这条特征**在正常流量里有多常见**？

- 常见 → 它只能当**反证**（扣分），不能当正证据。
- 罕见且专有（`grecaptcha-badge` 这种官方类名）→ 才能当正证据。
- 介于两者之间 → 配低权重，且**单独出现绝不触发处置**。

## 2. 正证据：强指纹从哪来

正证据分三层，原理不同：

| 层 | 抓什么 | 强度 | 条数 |
|---|---|---|---|
| `dom` | 网页 DOM：iframe src / class / id / 隐藏字段 | 强 | 34 |
| `window` | 桌面窗口：类名 / 标题 / 进程名 | 强 | 13 |
| `text` | 文本关键词（OCR 或 DOM 取回） | **弱** | 38 |

关键区别：**DOM 和 window 是强指纹（命中即高置信），
text 是弱指纹（需要多个词共现才敢下判断）。**

原因很直接：`#32770` 这个窗口类名除了系统对话框没别的东西用，
但"验证"两个字满世界都是。

### 2.1 来源台账（trust）

每条指纹都标了来源，来源带可信度。加新指纹时**必须**填来源，
否则来源不明的东西会慢慢污染整个模型：

| 来源 | trust | 条数 | 说明 |
|---|---|---|---|
| `probed-2026-09` | 1.00 | 38 | 本机 Edge + CDP 实测抓取，可信但样本少，升级后需重测 |
| `probed-windows` | 1.00 | 10 | 本机 EnumWindows 实测，系统窗口类名跨版本基本稳定 |
| `ms-docs` | 0.98 | 4 | Microsoft 官方文档 |
| `recaptcha-docs` | 0.95 | 7 | Google 官方公开约定 |
| `hcaptcha-docs` | 0.95 | 3 | hCaptcha 官方文档 |
| `cloudflare-docs` | 0.95 | 5 | Cloudflare 官方文档 / 长期稳定公开行为 |
| `geetest-docs` | 0.90 | 4 | 极验官方文档 / 前端公开类名（V4 类名有变，已低配权重兼容） |
| `aliyun-docs` | 0.90 | 2 | 阿里云验证码 2.0 文档 |
| `community-2024` | 0.60 | 6 | 社区整理。**过时风险最高，新报误报优先怀疑这一档** |
| `heuristic` | 0.40 | 6 | 纯启发式推断。**单独出现绝不触发处置** |

### 2.2 强词组（共现）

OCR 会把文本拆行、错字、乱序。"拖动滑块"可能被读成
"拖动"+"滑块"两行。所以除了单条指纹，还有 **9 组共现规则**
（`STRONG_TEXT_GROUPS`）：组内任一片语命中即视为高置信。

有两组特别值得记：

- `grp.otp.zh` —— **特意不含单字「验证码」**，因为误报太高
  （页脚"验证码"链接、"获取验证码"按钮）。必须是
  "短信验证码 / 获取验证码 / 请输入验证码 / 邮箱验证码"。
- `grp.challenge_page.en` —— severity 是 **`bypassable`**，
  因为 Cloudflare 无感盾等 1~2 秒自己就过了，
  这时候叫人反而是打扰。

## 3. 硬约束 #9：不硬解

**禁止写任何识别滑块缺口位置、点选图标坐标的逻辑。**

滑块 / 点选类指纹全部配成 `Severity.INTERRUPT`，
它们的 evidence 里带 `"machine_solve": "forbidden"` 作为
**可执行的自证** —— 任何人加硬解逻辑都会立刻和这里冲突。

检出滑块的目的**只有一个：叫人。** 不是"试着过一下"。

## 4. 三态：detected / unknown / clean

`RiskStatus` 有三个状态，且 `is_clean` 只在**明确干净**时为真：

| 状态 | `detected` | `is_clean` | 含义 |
|---|---|---|---|
| 检出 | True | False | 有指纹命中 |
| **未知** | False | **False** | 没查成（OCR 不可用、超时、枚举不到窗口、检测器抛异常） |
| 干净 | False | True | 查了，确实没有 |

**未知 ≠ 干净。** 这是整个模型里最容易写错的地方。

理由：`RiskStatus.action` 的定义是"没检出就 `continue`"，
所以**未知状态的 `action` 也会返回 `continue`**。
如果调用方拿 `action` 当判据，未知就被静默放行了 ——
结果就是"OCR 没装 → 一路绿灯 → 撞上验证题才报错"。

`unknown` 的合法取值只有
`clean` / `no_fingerprint` / `below_threshold` 三种 reason，
其余一律算未知。

## 5. 从"判定"到"处置"：ACTION_INTERFACE

判定是 5B 的事，处置是 5C 的事，两者的接缝是
`ACTION_INTERFACE`（`status.py`）：

| 动作 | 谁消费 | 失败时抛 | guard 入口 | 人能不能解决 |
|---|---|---|---|---|
| `continue` | 调用方自己 | — | 无 | 不需要人 |
| `pause` | `guard.pause_for_human` | `HumanInterventionTimeout` | `pause_for_human` | **能** |
| `abort` | 调用方自己 | `RiskBlocked` | 无 | **不能** |

`pause` 与 `abort` 的区别就一句话：**人能不能解决。**
能 → pause；不能 → abort。abort **不走 pause_for_human**，
那只会白等五分钟。

### 5.1 判定入口：`should_intervene`

**这一节在 2026-10-01 被修正过。** 修正前的规则是
"`is_clean=False` 一律熔断"，那会把 `bypassable` 也拦下来 ——
等于 guard 用"事实核对"覆盖了 5B 的"产品判断"。现在的规则是：

| `is_clean` | `detected` | 处置 | 理由 |
|---|---|---|---|
| `True` | 任意 | **放行** | 查过了，干净 |
| `False` | `False` | **熔断** | 未知 —— 5B **没做成判断** |
| `False` | `True` | `action == continue` → **放行** | 5B 判断过了，尊重它 |
| `False` | `True` | `action == pause` → **熔断** | 需要人 |
| `False` | `True` | `action == abort` → **熔断 + 抛 `RiskBlocked`** | 人来了也没用 |

### 5.2 核心不变式：guard 只在"5B 没判断"时越权

两种 `is_clean=False` 的情况**完全不同**，初版把它们混为一谈是错的：

- **`detected=False`（未知）** —— 5B **没做成判断**：
  OCR 没装、超时、检测器自己抛了异常、页面读不出来。
  这时候 guard **必须**保守熔断。放行等于盲开车。
- **`detected=True`（检出）** —— 5B **做了判断**，
  只是结论是"不必打断"（`bypassable`）。guard **尊重这个判断**。

一句话：**guard 只在"5B 没判断"时越权；5B 判断过了就听 5B 的。**

### 5.3 这个修正的代价（写清楚，别当没看见）

放行意味着：如果 5B 把某个**该拦的东西**错标成 `bypassable`，
guard 不会再兜住它。这是**刻意接受**的 —— 因为兜住的代价是
每次 Cloudflare 无感盾都白停五分钟，而那是常态。
防线在 5B 的 severity 配置上，不在这里。

### 5.4 这个取舍被钉在测试里

```
tests/test_phase5_guard.py::
  TestTranslateAction::test_bypassable_passes_because_action_continue
  TestTranslateAction::test_bypassable_was_the_only_case_that_changed
```

第二条尤其重要：改判据最容易出的事故是**顺手把未知也放行了**，
那是最危险的回归。它把四个 severity 的结果全部锁死。

## 5b. 误报率实测（5G，2026-10-01）

用 20 个**本地真实页面**（`tests/fixtures/normal_pages/`）跑 text 层：

```
误报率          ：1/20 = 5.0%
清零 footer 后  ：3/20 = 15.0%   ← 消融对比
```

**这两行数字是本模型最有力的自证。**

- **5.0%** —— 符合"最多 1 个误报"的要求。而这 20 个样本**不是干净文本**：
  注册页真的有"获取验证码"按钮、银行页面真的有"风险控制"和"短信验证码"、
  文档页真的有"正在初始化"。把危险词去掉再测，等于把体温计放进冰水。

- **15.0%** —— 把页脚档惩罚清零后，误报率**翻了三倍**。
  多出来的两个误报（`08_register` 0.30→2.70、`10_form_contact` -0.40→1.70）
  原本正是被页脚反证压住的。**这就是"页脚是最有力的反证"的量化证明。**

### 已知误报（刻意保留，未调参压掉）

`16_bank_dashboard.html` 会被误报（score 2.65）。命中：

```
txt.zh.sms_code(1.4), txt.zh.risk_control(1.0),
txt.zh.abnormal(1.0), txt.zh.verify_code(0.8)
```

银行网银的"安全提示"里必然出现这几个词。**没有偷偷降权压掉它** ——
因为一个 5% 的误报率如果连"误报的是哪一类"都说不清，这个数字就没有意义。

**修法建议**：这正是第 1 节那条原则的又一次应用 ——
「风险控制」「操作异常」在**金融类正常页面**里的普遍程度很高，
应该降权或移进弱词表。改权重属于指纹库的职责，留给后续批次。

### 三档消融的杠杆对比

| 档 | 清零后平均分抬高 |
|---|---|
| `footer` | 最大 |
| `ambiguous` | 中 |
| `ocr_noise` | 最小 |

`footer` 的杠杆**必须**大于 `ocr_noise` —— 这条被断言在
`TestAblation::test_footer_penalty_is_the_largest_lever` 里。
如果哪天有人把页脚权重调到比 OCR 噪声还轻，那条会红。

## 6. 降级规则（detector.py）

三层检测不是"三个都跑一遍然后投票"，而是**逐层降级**：

1. 总预算是三层**共享**的（默认 3.0s），按各层期望耗时
   15 : 10 : 200 分配，不是每层 3s。
2. 逐层跑，剩余预算不够最小层预算（0.05s）就跳过该层。
3. **某一层命中即立刻返回**（`extra["stopped_at"]`），
   不浪费预算去跑更慢的层。
4. 某层抛异常 → 记进 `errors`，转成未知状态参与合并，
   **继续跑下一层**（一层坏不该让整个检测器瞎掉）。
5. 三层跑完 → `merge_status`。合并有一条额外闸门：
   **只要有一层是未知，整体不许判干净**（强制降级为未知）。

`detect_quick()` = 总预算 1.0s + 跳过 pixel 层。

## 7. 误报率怎么测（留给 5G）

三条现成的杠杆：

1. **分档消融**：`penalty_scale={WEAK_TIER_FOOTER: 0.0}`
   逐档关掉，看误报率变化，量出每档的边际贡献。
2. **来源审计**：`audit_sources()` 列出每条指纹的来源与可信度。
   新报误报时**优先怀疑 `community-2024`（trust 0.6）和
   `heuristic`（trust 0.4）这两档**。
3. **可解释性底线**：每个结果都带 `extra["layers"]`
   和 `weak_detail`（逐词列出命中了哪档、实扣多少分）。
   任何一次判定都能回答"这个 -0.6 是哪来的"。

**测试集要包含的负面样本**（正常页面但含风险词）：
电商页脚、论坛登录页、"验证邮箱"的注册流程、
带 cookie 弹窗的新闻站、任何有"正在加载"的 SPA。

## 8. 能力边界

本模型**不做**：

- **不硬解**（硬约束 #9）—— 检出滑块/点选只为叫人，
  不尝试识别缺口位置或图标坐标。
- **不猜验证码内容** —— OTP 类指纹全部 `INTERRUPT`，
  机器不去猜短信/邮件里的数字。
- **不在未知时自作主张放行** —— 未知一律按可疑处理，
  但"要不要因此中止"是调用方的决定（`ACTION_INTERFACE`
  的 `note` 里写明了这一点）。
- **不做文本归一化** —— 归一化在 `detector_pixel` 层，
  指纹库只做匹配。这样指纹库可以独立测试。
- **不决定重试上限** —— 那是业务决定，不是技术决定。
